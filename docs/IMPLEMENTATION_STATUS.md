# 实现与验证记录

下文保留 v0.1 真实消息验证，以及当时的限制。当前实现是 v0.3，以 [README](../README.md) 和 [v0.3 说明](V03_SCOPE.md) 为准。v0.2 批量记录见 [v0.2 说明](V02_BATCH.md)。其中 SHA-256 与手动界面的描述已被后续版本替代。

记录日期：2026-09-30。保留 Pro；实现依据为已登录的 SaleSmartly 网页，不依赖官方 OpenAPI 媒体下载能力。

## 已实现

1. 扩展仅选择当前 Chrome Profile 内 `https://app.salesmartly.com/*` 标签页；网页内面板由用户点击扩展图标打开。
2. 默认使用页面 Fetch/XHR 响应观察器，读取已选 SaleSmartly 页面的后续聊天响应。保留 debugger Network/WebSocket 观察器用于后续专项适配。停止页面观察时恢复原函数，不修改请求参数或响应。
3. 消息按项目、渠道账号、客户、会话和源消息 ID 隔离；大整数 ID 不转换为不精确浮点数。缺少稳定身份时保留诊断。
4. Native Messaging 使用长度前缀、请求 ID 和 ACK。待写队列保存在 IndexedDB，最多 8 MB；溢出暂停。数据库事务提交后才回复 ACK，重复批次不会重复入库。
5. Chrome 下载媒体后，助手按注册任务 ID、下载 ID、专用目录和文件主体名称核对文件，允许 Chrome 根据响应格式调整扩展名，校验非空及类型，计算 SHA-256，原子落盘。保留 Chrome 下载暂存文件，避免误删其他下载。
6. 导出会话为独立 HTML、JSONL、版本记录、媒体和缺失清单。HTML 对正文进行转义，禁止脚本和远程资源加载。
7. Windows 原生启动器使用系统 .NET Framework 编译，启动现有 Node 24，逐段转发并刷新管道缓冲区，不启动新 Chrome 或新登录 Profile。
8. 超过普通批次上限的单条消息使用分块传输，重组后提交并确认；扩展重新加载后，打开图标会替换残留旧面板。

## 已验证

- TypeScript 静态检查通过。
- 18 项测试通过：长 ID、文本链接、真实 `content.msg` 媒体字段与收发方向、晚返回响应的身份、凭据字段脱敏、不同项目隔离、消息版本、事务回滚、ACK 重试、媒体改扩展名后的导入、HTML 转义、大消息分块与坏帧、Fetch/XHR 观察器不消耗原响应及停止恢复。
- 实际 Windows `.exe` 启动器 → Node 原生消息协议 → SQLite 写入和重复 ACK 验证通过，使用隔离合成数据。首条回复在输入管道保持打开时到达，覆盖此前启动器缓冲导致的等待问题。
- 合成会话 5 条消息，PNG、WAV、由本机 ffmpeg 生成的 MP4 成功入库并导出，缺失媒体数为 0。
- 已连接用户指定的 `realismthriftglobal.com` Chrome Profile，观察到真实 SaleSmartly Pro 会话页面采用 Vue 虚拟消息列表。消息 DOM 未直接提供稳定源消息 ID，支持优先观察网络响应的实现选择。
- 本地助手已注册到当前用户。用户已批准并手动加载自定义扩展。

首轮 debugger 实测未收到可入库响应，改用页面响应观察器成功取得真实数据。实际历史接口为网页自身的 `chat/chat-user/get-message-list`。记录含稳定 `mid`、客户/会话 ID、毫秒时间、`sender_type`，媒体地址位于 `content.msg`；缺少渠道账号标识时保留 `unknown` 与警告。

本轮已采集 2 位客户、84 条真实消息，包括文本、图片、语音、视频、贴纸、通话日志和系统记录。此前超出普通批次上限的 521,398 字符贴纸记录已通过新版分块协议完整入库，不再遗漏。通话日志和未知类型保留原始结构。

最先保存的真实样本：JPEG 77,764 字节，588×1280；Ogg/Opus 33,553 字节，12.9465 秒；MP4/H.264+AAC 4,039,046 字节，576×1024、19.2333 秒。ffprobe 可读取三者，视频完整解码通过。此结果只证明这些已测文件可用，不能证明图片为平台上传原图，也不能推及所有渠道/素材。

最终共保存 6 个真实媒体：2 张 JPEG、1 条 Ogg/Opus、2 段 MP4 和 1 个动画 WebP。第二段视频为 43.5333 秒、544×960，完整解码通过；动画贴纸为 512×512、20 帧，Pillow 逐帧读取通过，Chrome 可显示。ffprobe 对该动画 WebP 报解码提示，未将其作为贴纸验收依据。

已通过新版网页面板导出两个独立样本包，各 42 条消息，媒体缺失均为 0。含媒体的包保存 6 个文件、共 12,284,465 字节。`tools/verify-export.ts` 在不连接浏览器或助手时检查 JSONL/manifest/HTML 数量、缺失占位、相对资源路径、文件大小及 SHA-256，全部通过。将该包作为独立目录在本机浏览器预览，图片、视频元数据和动画贴纸可正常读取，资源均指向本地副本。

本机实际包位于 `.local/archive/exports/3374f5f72783-1790747852955-7c48e2f6/` 与 `.local/archive/exports/146c5013b795-1790747936060-4f15aaab/`，客户数据未加入源码或测试夹具。验收截图保存在 `.local/verification/`。

## 本轮范围及下一步

首版为“用户加载会话历史，扩展观察并归档”。下一步以真实网络响应校准消息字段、媒体原始地址和分页证据，再实现受控历史遍历及多个会话调度。未达到明确边界的归档保持 `unknown`；不能靠滚动几轮、DOM 数量稳定或空响应推断完整。

v0.3 已实现左侧“全部”的客户遍历和历史上滚。全账号真实范围仍未验收。尚未实现：Blob/分段媒体读取、已验证的最早历史边界、完整撤回/删除语义、SQLite 在线备份工具、托盘应用和 AI 回复。
