# v0.2.1 批量采集修复

2026-09-30 至 2026-10-01（UTC+8）。用户反馈：设置日期和全部客户后，采集页只不断滚动左侧客户列表，没有加载聊天历史。

## 已确认的问题

- 原任务已发现 550 位客户，全部仍为 waiting，观察/新增/更新/重复消息数均为 0。原数据库保持 196 条消息、281 条历史版本、16 个媒体。
- v0.2 的控制器先执行整个客户列表枚举，之后才开始聊天采集。客户多时，任何暂停都会发生在第一条聊天采集之前。上次仅两位客户的限量验收跳过了长时间枚举，不能证明无限客户流程。
- 真实页面中点击客户姓名可以返回消息预取数据，却不改变当前选中的会话；这会让历史滚动作用于上一位客户。改为点击完整 `.session-item` 会话卡片，当前选中状态确实随之切换。
- 深处断点恢复后，网页只重新加载前 50 位客户。旧定位逻辑滚到底后仅等 150 ms 就结束，下一页尚未返回，导致把队列中的后续客户误判为不在筛选列表。

## 修复

- 改为边发现边采集：先处理 SQLite 中已发现的客户，再翻下一批列表。暂停后优先处理原队列，已完成客户跳过，当前客户重载并按平台 ID 去重。
- 分页偏移按实际队列行数推进，避免不足 200 位的一批客户导致后续客户被跳过。重复列表响应不算新客户进展，防止未知末尾无限滚动。
- 恢复时定位队列中的深处客户，会重新进入列表底部加载区并等待列表增长或目标卡片出现；末尾标志后也留出最后一帧渲染。等待有上限，定位失败保留为可重试缺口，不推断客户已消失。
- 点击完整会话卡片，等待目标卡片成为当前选中会话；选择未成功则记录缺口，不滚动其他客户的历史。每页历史在本地提交后才继续。
- 首个会话响应可能早于筛选核对或客户选择；暂存该响应，核对通过且客户 ID 匹配后通过正常分片/提交路径入库。即使网页已经打开该客户、再次点击不会发新请求，也能接着加载历史。测试确认另一客户的数据不混入，SQLite ACK 前不推进。
- 适配真实网页历史游标：完整返回结构中 `next_pk` 包含客户/sequence_id 时继续，`next_pk={}` 且 `package_limit=0` 时确认末尾。缺字段不推断末尾；网页套餐限制单独记为缺口。
- 面板区分已发现/已处理/待处理客户、已确认范围和缺口；显示当前客户、已检查条数和加载到的日期，以及本次消息写入数量。日期含义明确为所选日期到任务启动时。
- “更多选项”显示客户缺口及原因；部分完成的任务可以点击“重试未完成部分”，保留已完成客户和已有数据。恢复时清理遗留的 running 状态，避免多位客户同时显示正在处理。
- 客户列表与历史响应保留少量分页结构诊断，便于依据真实返回字段确认末尾；不保存完整客户列表正文或请求凭据。未确认末尾仍标为缺口，不能用超时假装成功。
- 延续原 SQLite 去重和媒体路径复用，没有加入 SHA-256 扫描、服务端或新权限。
